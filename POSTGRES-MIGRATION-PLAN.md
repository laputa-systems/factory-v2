# PostgreSQL / SQLx hard-migration plan

## Outcome and non-goals

Replace SQLite with PostgreSQL through SQLx. PostgreSQL is the sole mutable
ledger authority for `societyd`, `societyctl`, CL-001, and every active test.
There is no store trait, driver switch, dual write, SQLite fallback, or
long-lived compatibility mode.

The current ignored `var/` databases are disposable prototype state. Archive
any separately required research artifacts, create a fresh PostgreSQL ledger,
and rerun founding and CL-001 setup. This is both faster and more rigorous than
calling unverified prototype state a migration. A SQLite importer is explicitly
out of scope; if preservation later becomes required, it needs its own approved
data-provenance design and one-shot tool.

This migration does not introduce a distributed daemon, generic async
application architecture, an ORM, generic SQL payloads, or changed command,
event, replay, content, socket, or authority contracts.

## Fixed decisions

- **Development service:** PostgreSQL 18 from Homebrew is the local baseline;
  `brew services start postgresql@18` starts it. CI and operators provide a
  supported PostgreSQL 18-compatible service separately.
- **Dependencies:** before editing `Cargo.toml`, record the then-current
  stable exact versions of `sqlx` and `tokio` in `DEPENDENCIES.md`.
  Enable only SQLx `postgres`, `runtime-tokio`, and a Rustls TLS feature;
  do not enable SQLx macros, SQLite, `any`, or another runtime.
- **Execution shape:** preserve the synchronous `KernelStore` public API.
  It owns one Tokio current-thread runtime and a bounded `PgPool`; each
  method runs its SQLx future on that owned runtime. This is one explicit
  storage boundary, not per-method runtime construction or workspace-wide
  async contagion. The existing daemon serializes command acceptance, so
  PostgreSQL concurrency is used only where an operation deliberately needs it.
- **Connection policy:** `KernelDatabaseUrl` parses a PostgreSQL URL, rejects
  an empty value and insecure remote TLS, and never logs credentials. A
  migration-capable role applies schema revisions; the daemon role has only
  runtime DML privileges. Local development may use one owner role only if that
  role split is documented as deferred local setup rather than implied.
- **Authority locks:** retain `societyd.lock` because it protects the
  runtime-root socket and files. Also acquire a PostgreSQL advisory lock on one
  dedicated checked-out connection for the daemon lifetime. Never acquire the
  advisory lock through a pooled one-shot query, where release can silently
  drop it.
- **SQL contract:** retain `BIGINT GENERATED BY DEFAULT AS IDENTITY` for
  internal numeric IDs, numeric enum codecs with named `CHECK` constraints,
  and `BYTEA` for binary identities. Use `INSERT ... RETURNING`, PostgreSQL
  `$N` placeholders, typed SQLx decoders, transactions, and explicit
  `SELECT ... FOR UPDATE` only for the documented state/generation guards.
  Never translate database error text into domain policy.
- **Schema contract:** PostgreSQL SQLx migrations are the sole canonical
  bootstrap. Every SQLite table, foreign key, check, unique or partial index,
  and trigger is either reproduced as a named PostgreSQL constraint/index/
  trigger or replaced by a narrower typed transaction precondition with an
  observable regression test. No silent weakening is permitted.
- **Tests:** `SOCIETY_POSTGRES_TEST_URL` names an administrator-approved test
  database, not a production URL. The harness creates a generated private
  schema per test, applies the SQLx migrator in that schema, sets the pool's
  search path on every acquired connection, and drops the schema afterward.
  It supports parallel tests without a test database per case.

## Phase 1 — prove the target and build the PostgreSQL foundation

**One cohesive commit:** PostgreSQL configuration, dependencies, migrator, test
harness, and schema contract. Do not commit exploratory inventories or a
partial SQL conversion.

1. Create `docs/postgres-migration-inventory.md`. It is a concise checked
   checklist, not a prose rewrite: enumerate the 2,417-line
   `migrations/0001_kernel.sql` objects, the SQLite triggers, the
   `KernelStore` transaction envelope, all `last_insert_rowid` sites, and
   the seven direct `KernelStore` client/test areas. Mark each target object
   as schema, SQL helper, or behavioral-test evidence.
2. Approve exact SQLx/Tokio versions in `DEPENDENCIES.md`; add no other
   direct dependency. Add `KernelDatabaseUrl`, redacted configuration errors,
   bounded-pool construction, and a reusable owned-runtime store shell.
3. Replace the SQLite bootstrap with ordered
   `migrations/postgres/` SQLx migrations. Translate the complete schema in
   dependency order in the same phase, including every partial index and all
   trigger invariants. Use `BIGINT`, `BOOLEAN`, `BYTEA`, and explicit
   `TEXT` deliberately; do not run a search-and-replace conversion.
4. Add the real PostgreSQL harness and catalog tests. Assert fresh migration,
   second migration, expected tables/constraints/indexes/triggers, and the
   critical invariant rejections. Test the daemon advisory-lock contention on
   two independent dedicated connections.

Nearest judges:

```text
SOCIETY_POSTGRES_TEST_URL=... cargo test -p society-kernel --test postgres_harness -- --test-threads=1
SOCIETY_POSTGRES_TEST_URL=... cargo test -p society-kernel --test postgres_schema_contract -- --test-threads=1
```

## Phase 2 — port the whole kernel behind its existing boundary

**One cohesive commit:** all `KernelStore` and `study.rs` SQLx work plus
kernel contract tests. This is the large implementation phase; use local
checkpoints, not a stream of tiny commits.

1. Port the shared transaction envelope first: command identity/fingerprint,
   existing-receipt resolution, rejected command persistence, command body,
   accepted event, event body, materialized projection, and replay. Use a
   single `PgTransaction` from command lookup through commit.
2. Add narrow SQLx helpers for exactly the repeated operations: optional
   single-row decode, required scalar decode, returned identity conversion,
   typed digest decode, and closed enum decoding. Keep SQL adjacent to the
   specific transition; do not create a generic repository/row-map layer.
3. Port transition families in existing source order, retaining their current
   private function boundaries: constitutional/cycle/budget; projects/graphs;
   execution/content; native-child/Pi; then the isolated `study.rs` family.
   At each family boundary, run its existing contract test against PostgreSQL
   before proceeding, but do not commit it separately.
4. For every `last_insert_rowid`, use statement-local `RETURNING id`. For
   every SQLite `Immediate` transaction, identify the actual protected
   predicate: preserve serial daemon dispatch where sufficient; use row locks
   or a bounded serializable retry only where two PostgreSQL sessions can
   legitimately contend.
5. Preserve all tamper/replay cases. Add real-database regressions for duplicate
   command IDs, same-ID different body, stale generation, rejected-command
   durability, advisory-lock exclusion, and each PostgreSQL-specific
   trigger/constraint replacement.

Local checkpoints, in order:

```text
cargo test -p society-kernel --test founding_cycle_ledger -- --test-threads=1
cargo test -p society-kernel --test execution_foundation -- --test-threads=1
cargo test -p society-kernel --test study_forum -- --test-threads=1
```

The phase gate is all kernel tests using `SOCIETY_POSTGRES_TEST_URL`, followed
by a restart/reopen replay test that constructs a second `KernelStore` from
the same PostgreSQL schema and validates materialized state.

## Phase 3 — move the resident boundary and remove SQLite

**One cohesive commit:** daemon configuration, callers/tests, deletion, docs,
and final acceptance. Do not retain a feature flag after this phase.

1. Replace `runtime_root/society.sqlite3` opening and permissions checks in
   `societyd` with `KernelDatabaseUrl`, migration revision/replay checks,
   the retained local runtime lock, and the dedicated database advisory lock.
   Preserve content-root and Unix-socket ownership protections unchanged.
2. Update `societyctl`, `societyd` content/Pi code, CL-001 harnesses, and
   all kernel/daemon fixtures to create a PostgreSQL test schema rather than
   call `open_in_memory` or manufacture SQLite files. Keep the public socket
   protocol and the daemon's serial command loop synchronous.
3. Delete `rusqlite`, bundled SQLite transitive dependencies, the SQLite
   bootstrap, `society.sqlite3` constants, SQLite file tests, and all active
   SQLite documentation. The only allowed textual SQLite occurrence is a dated
   historical note explaining this hard cutover.
4. Update `AGENTS.md`, `ARCHITECTURE.md`, `DEPENDENCIES.md`, `README.md`,
   and test/operator instructions. Document PostgreSQL 18 setup, required
   URLs/roles, schema migration, backup/restore, health, advisory-lock, and
   replay diagnostics.

Final acceptance:

```text
rg -n 'rusqlite|sqlite3|PRAGMA|open_in_memory|society\\.sqlite3' --glob '!POSTGRES-MIGRATION-PLAN.md'
cargo fmt --all --check
SOCIETY_POSTGRES_TEST_URL=... cargo test --workspace --all-features -- --test-threads=1
cargo clippy --workspace --all-features --all-targets -- -D warnings
tests/generic-boundary/run-no-application-knowledge.sh
```

Finally restore a clean PostgreSQL backup into a blank database and require
`validate_replayed_materialized_state` to pass before the daemon accepts a
new command.

## Execution rules

- Make exactly one normal commit per phase. Keep a phase branch/worktree
  uncommitted until its phase gate passes; amend only that phase commit while
  addressing its own failures.
- Do not parallelize `store.rs` or `study.rs`. A secondary agent may only
  inventory a preassigned non-overlapping schema/trigger section or test
  fixture; the primary agent integrates all store SQL.
- Search first, then port a coherent function family, then run its nearest
  existing behavioral judge. Do not run full workspace validation after every
  family.
- If an existing SQLite behavior depends on a feature with no direct
  PostgreSQL equivalent, record the intended invariant and prove the selected
  PostgreSQL mechanism with a focused real-database test before proceeding.
