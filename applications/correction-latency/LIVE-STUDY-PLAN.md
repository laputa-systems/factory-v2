# CL-001 staged live-study plan

## Status

This is a sealed planning protocol, not a native-runtime qualification, paid
execution, or scientific result. The kernel now has a typed
PiSdkQualificationV1 lifecycle: a complete daemon-owned child custody chain
can promote the native profile and then close the bootstrap lab before a
separately identified live cycle is admitted. The resident can consume an
atomic qualification-launch claim through a supervisor-installed pinned
host/session profile, and can consume a sealed study-lifetime claim through
the same private profile boundary. That provider-free path is not an actual
qualification. No real host artifacts, auth/catalog material, qualification
ceiling, or actual qualification evidence has been installed, so the native
Pi profile remains unqualified in every real deployment. The durable,
root-owned 64-lifetime allocation mechanism and concrete
`ResidentPilotExecutionBackend` are implemented. The backend admits the
sealed plan, constructs its exact source/successor study transitions,
provisions the 64 M3 allocations through an operator-supplied Root Authority,
drives only claim-gated native lifetimes, and reads only closed pair/run
projections. Rebuilding it with the same operation identities skips completed
obligations instead of prompting them again. No real allocation manifest has
been admitted. Therefore no current artifact answers either CL-001's
retained-versus-reset treatment question or the broader institutional-state
question.

The application now has one deliberately narrow live-output boundary:
after an episode has no active obligations,
`StudyAdmissionAuthority::post_actor_public_forum` returns its bounded,
attributable public F0 record only. CL-001 accepts a decision only when its
decision seat has published one non-retracted `Synthesis` whose complete body
matches `cl-001|decision-record|v2|outcome=<0-or-1>|confidence=<low-medium-high>`.
The application records that exact body with its Forum-message citation. It
does not read a Pi transcript or infer a decision from model prose; a missing,
duplicate, or malformed declaration becomes an unavailable analysis input.
For a completed native actor, generic `RecordDecision` accepts only a citation
to that actor's own already-published public message, so disposal cannot be
used to manufacture an uncited posthumous decision.

study_program.rs keeps three stages separate: an optional cheapest paid adapter
smoke, a feasibility pilot, and a later substantive study. A result from one stage is
never silently repurposed as evidence from a later stage.

## Stage protocol

### 1. Optional cheapest paid adapter smoke

make run-society-cheapest-paid-smoke is a fixed $0.05 adapter smoke. It is pinned to the
candidate treatment above and rejects a provider/model override. It retains
qualification-artifact.json with provider usage, cost, Forum calls, artifact
digests, and integer guardrails.

Its topology remains one in-memory Forum shared across 16 reduced-role cells;
treatment labels are report metadata only, and it has neither PostgreSQL nor
daemon custody. It can expose adapter failure, provider availability, runtime
drift, or cost infeasibility. It cannot qualify the generic native profile yet
and cannot estimate a CL-001 treatment effect. It is not a release gate: run
it only when that adapter diagnosis is needed, and never enter it in a CL-001
estimator.

### 2. Feasibility pilot

After a real native qualification path and daemon backend exist, construct a
LiveRunPlan with exactly two independently generated pair IDs and world-seed
digests. Wrap it in FeasibilityPilotPlan; construction rejects any other pair
count or a plan under a different runtime identity. The application-owned
`CanonicalPilotRunner` now seals this exact plan, registers both pair seeds,
and owns the typed barrier state; it accepts no analysis artifact until the
daemon backend reports the completed run.

For each pair, run one retained and one reset arm using the exact eight source
and eight successor roles. Preserve the source freeze, successor-exposure
barrier, atomic matched correction release, terminal actor disposal, truth
reveal, typed measurements, and replay validation in VERTICAL-SLICE.md. Keep
the eleven pre-registered metric slots, complete-case rule,
retained-minus-reset estimand, and precision targets in the sealed LiveRunPlan.

Retain raw receipt/transcript/content identities, the sealed plan and runtime
digests, pair/seed registration, both cost measurements, every unavailable or
invalidated state, and the planned analysis artifact. The pilot is a
feasibility and variance observation, not a confirmatory estimate.

### 3. Substantive study

Analyze the closed pilot only under its pilot plan. Use observed paired variance
and the declared per-metric precision targets to choose a new finite pair count
and request a new spend authorization. Before new outcomes are visible, seal a
new LiveRunPlan and construct SubstantiveStudyPlan with the pilot
analysis-artifact digest.

SubstantiveStudyPlan rejects a changed runtime actor policy, a reference to
another pilot, and reuse of either a pilot pair ID or world seed. It deliberately
does not assign a sample size, confidence claim, or spend ceiling. Those are a
post-pilot, separately authorized decision.

## Release gates before a canonical pilot

1. The dependency lock, Pi host build, and Rust peer agree on the sealed
   0.84.1 runtime identity.
2. The resident has `PinnedPiLaunchProfile`, daemon-private workspace
   materialization, and a claim-only qualification opener. Before execution,
   a supervisor must install the exact host artifacts, Pi runtime identity,
   private auth/catalog source, Forum contract, and a separately assigned
   qualification ceiling. Its opaque `runtime_profile_digest` must equal the
   `CanonicalLiveRuntimeProfile` sealed digest in the pilot plan; the concrete
   backend checks this before its first study admission. It must then obtain
   actual trusted qualification evidence. The current Unqualified state is
   never relabeled by an adapter artifact.
3. The daemon exposes a public generic admission/scheduling route that can
   seal the application plan, construct all task starts, drive paired barriers,
   and close the run. `CanonicalPilotRunner` owns the application barriers and
   `DaemonComposition` seals the opaque `LiveRunPlan`, and
   `TaskAttemptRunner` can now open only from a durable kernel launch claim.
   Its raw start input is crate-private. `StudyPlanLifetimeKey` binds a
   sealed run identity and pair/arm/phase/role selector to a durable,
   root-owned `AllocateStudyActorWork` manifest entry; accepting that entry
   atomically leases its exact ready M3 work item for its already admitted
   actor. The daemon validates the selected obligation, derives its private
   workspace, and resumes accepted claims by deterministic command identity.
   Application-sealed prompt content now carries the exact content-registration
   event needed for the TaskAttempt frontier fence.
   A reconciled `TaskAttemptRunner` can now record the terminal actor
   obligation under a daemon-derived completion identity; it cannot close a
   live actor before its native custody suffix is complete.
   `NativeTaskAttemptDriver` advances the claim-gated Pi lifecycle, routes
   every Forum call through the daemon, and begins bounded containment on a
   failed live attempt. The application accepts decision output only through
   `terminal_public_forum_decision` and the post-actor public-Forum boundary
   described above. `ResidentPilotExecutionBackend` is the concrete
   `PilotExecutionBackend`: it emits no raw M3 or native identity, invokes
   `RootStudyM3ProvisioningAuthority` only with `ResidentPilotM3Authority`'s
   explicit operator facts, provisions exactly 64 allocations before
   `StartStudyRun`, and rebuilds completed-seat state through bounded generic
   obligation projections. This implementation gate is closed. Its operational
   subgate remains: a real Root Authority must admit that manifest under a
   live qualified cycle. The application cannot manufacture or inspect any
   M3/native identity.
4. A fresh PostgreSQL schema at society-kernel-postgres-schema-v20, content
   custody, daemon replay, and all focused provider-free judges pass.
5. The exact pilot seeds, pair labels, runtime artifact identities, analysis
   targets, and $0.20 pilot cap are sealed before pilot actors are admitted.

Until all five gates hold, do not treat the adapter smoke, provider-free
harness, or a planning digest as live-study data.
